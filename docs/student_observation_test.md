# 1번 관측 시험 계획

## 목적
CAD를 확정하기 전에, 현재 USD와 현재 계단 teacher로 student에게 어떤 입력이 필요한지 확인한다.
여기서 나온 student는 판단용이며, 실물에 쓸 student는 재학습한 teacher로 다시 증류한다.

## 시험 구성
| student | 관절 입력 | 높이맵 | 상태 |
|---|---|---|---|
| A | 실제 관절각, 관절 속도 | 있음 | 구현됨 |
| B | 명령 관절각만 (`last_action`) | 있음 | 구현됨 |
| D | A와 동일 | 없음 | 예정 |

세 student의 공통 입력:
- IMU: `base_ang_vel`, `projected_gravity`
- 발 접촉 6개: 수직 힘 1N 초과 여부 (수직면에 부딪힌 tibia는 접촉으로 치지 않음)
- `last_action`

높이맵은 계단 형상에서 계산한 가짜 라이다다.
- 범위: 몸통 기준 x -0.24 ~ +0.56m (2cm 간격), y -0.2 ~ +0.2m (10cm 간격), 205칸
- 몸통 위치와 yaw를 따라가고, 표준편차 1cm 노이즈를 더한다.
- 몸 아래와 뒤쪽도 보이는 이상적인 시야다. L2 시야 제한은 2번 장착 시험에서 넣는다.

## 학습 설정
- teacher: 현재 계단 teacher 체크포인트 (관측 91차원, MLP)
- student: GRU 256 + MLP [256, 128]
- 시작 상태: 저장 버퍼를 쓰지 않는다 (`buffer_ratio=0`). 실제 운용처럼 기억이 빈 상태에서 계단 앞부터 시작하고, `stair_success`가 곧 처음부터 끝까지 오른 비율이 된다.

## 액추에이터는 2단계로 시험
현재 teacher는 처짐과 지연을 학습한 적이 없어서, 지금 넣으면 teacher 자체가 무너져 student 문제와 구분되지 않는다.
1. 현재 액추에이터로 A, B, D를 비교한다.
2. 처짐과 지연을 넣은 teacher를 재학습한 뒤, A와 B를 다시 비교한다. 값은 서보 실측으로 정한다.

## 판단 기준
판단은 학습 로그가 아니라 `scripts/eval_stairs.py`의 꼭대기 도달 비율로 한다. teacher와 student를 같은 조건(저장 버퍼 없음, 노이즈 없는 평균 행동, 환경당 첫 에피소드만 집계)으로 잰다. 10%p 기준은 임시값이다.
학습 중에는 `Metrics/stair_reached_top`, `Metrics/stair_move`(최대 17), `Loss/behavior`로 진행을 본다. A와 B는 같은 teacher 체크포인트, 같은 `num_envs`로 돌린다.

| 결과 | 판단 |
|---|---|
| A가 teacher보다 크게 낮음 | 센서 문제가 아니다. 증류 설정이나 teacher를 먼저 본다 |
| 1단계에서 B가 A보다 10%p 넘게 낮음 | 처짐이 작은 조건에서도 관절 입력이 필요하다. 서보 포텐셔미터 신호 읽기를 검토한다 |
| 1단계에서 B가 A와 10%p 이내 | 결론을 내리지 않는다. 지금은 실제 관절각이 명령값과 거의 같으므로 2단계에서 다시 비교한다 |
| 2단계에서 B가 A와 10%p 이내 | 관절 피드백 회로 없이 간다 |
| 2단계에서 B가 A보다 10%p 넘게 낮음 | 서보 포텐셔미터 신호 읽기를 검토한다 |
| D가 A와 10%p 이내 | student가 동작을 외운 것이다. 시험을 무효로 보고 계단 위치와 yaw를 무작위화한다 |

## 원인 분리 시험
A가 teacher보다 크게 낮아서, A와 같은 teacher로 한 가지씩만 바꿔 학습한다. 실물에 쓸 설정이 아니다.

| task | 바꾸는 것 | 오르면 뜻하는 것 |
|---|---|---|
| `Hexapod-Stair-Student-A-Phase` | student 입력에 단계 번호(6차원) 추가 | 단계를 추정하지 못하는 것이 원인 |
| `Hexapod-Stair-Student-A-TopEnd` | 정지 단계에 들어서면 에피소드 종료 | 꼭대기 데이터가 학습을 방해한 것이 원인 |

둘 다 그대로면 발 위치 정밀도와 학습 설정을 본다.

A-Phase가 올랐으므로, 단계 번호 없이 student가 단계를 추정하도록 기억 학습 구간을 늘려 시험한다. 환경은 A-TopEnd와 같다.

| task | `gradient_length` | `num_steps_per_env` | 기억 학습 구간 |
|---|---|---|---|
| `Hexapod-Stair-Student-A-TopEnd` (기준) | 64 | 128 | 1.28초 |
| `Hexapod-Stair-Student-A-Mem128` | 128 | 128 | 2.56초 |
| `Hexapod-Stair-Student-A-Mem256` | 256 | 256 | 5.12초 |

## 진행 순서
1. teacher, A 평가 (완료)
2. A-Phase, A-TopEnd 학습 및 평가
3. 증류 설정을 정한 뒤 A, B 재비교, D 추가
4. 비교 결과를 이 문서에 기록

## 결과
`scripts/eval_stairs.py`, 4096대.

| | 꼭대기 도달 | 계단 앞 시작만 | 넘어짐 (`bad_ori`) | 정지 성공 |
|---|---|---|---|---|
| teacher `model_6200` | 98.2% | 98.2% | 2.0% | 0% |
| A | 75.8% | 74.8% | 18.8% | 0% |

- A의 실패 993건 중 발을 옮기는 단계가 905건(91%)이다. 앞발 335, 중간발 260, 뒷발 310, 전진 87, 나머지 1건.
- teacher도 A도 대부분 단계 16(정지)에 머물다 45초 시간 초과로 끝난다. `stair_success`가 0인 것은 기록 오류가 아니다.
- 원인 분리 시험 (사용자 보고, 평가 스크립트 값인지 미확인): A-TopEnd 약 0.8, A-Phase 0.9점대. 단계를 추정하지 못하는 것이 차이의 주된 원인으로 보이고, 꼭대기 데이터는 학습 속도에만 영향을 준 것으로 보인다.
- `Metrics/success_rate`는 계단 성공률이 아니라 Isaac Lab의 속도 명령(`base_velocity`)이 기록하는 속도 추종 지표다. 판단에 쓰지 않는다.

## 2026-11-07 단계 전환·충돌 피드백 반영

피드백의 보행 순서와 단계 전환 설명은 맞다. 앞발 다음에는 중간발을 옮기며,
옮기는 두 발의 위치·지형 높이·접촉을 함께 검사한다. `feet_up`은 몸통 전진 **보상**의 조건이고
관절 위치 명령을 제한하지 않는다. 다만 몸통·coxa·femur 접촉에는 이미 `undesired_contacts` 벌점이 있다.
이것은 충돌을 예방하는 제어나 단계 전환의 충돌 여유 검사와는 다르다.

확인된 문제는 다음과 같이 수정했다.

- 발을 들기 전에 전진한 거리도 몸통 최고 위치 기록에 반영한다. 나중에 발을 들었을 때 그 거리를 소급 보상하지 않는다.
- 전진 완료는 과거 최고 위치 대신 현재 몸통 위치로 판단한다. 목표에 닿았다가 후퇴한 상태로 완료되지 않는다.
- MOVE 중 나머지 지지발에 기존 위치 조건과 `air_time == 0`을 함께 요구한다.
  이미 읽는 `(환경 수, 6)` 접촉 정보이므로 별도의 숫자 입력이나 센서 배선 코드가 필요하지 않다.
  ADVANCE에는 추가 접촉 조건을 적용하지 않는다. 발을 번갈아 드는 전진 동작을 제한하지 않기 위해서다.
  옮기는 발은 지지발 검사에서 제외하며 기존 `on_target`의 위치·높이·접촉 조건으로 착지를 검사한다.
  정지 완료의 여섯 발 접촉 검사와 단 끝에 닿는 `edge_touch` 판정도 유지한다.
- `StairGaitCfg.move_contact_hold_time`으로 MOVE 완료 조건을 여러 정책 step 동안 유지하도록 설정할 수 있다.
  기본값은 `0.0s`다. `0.10s` 같은 값은 실험용이며, 기존 teacher의 동작을 막지 않는지 재평가한 뒤 정한다.
  조건이 한 번이라도 깨지거나 단계·에피소드가 바뀌면 누적 시간이 초기화된다. ADVANCE에는 이 시간을 적용하지 않는다.

`air_time == 0`은 tibia 링크의 접촉 판정이어서 수직면 접촉과 하중을 받는 지지를 구별하지 못한다.
지형 위치 조건을 함께 검사하지만 발끝 접촉이나 무게중심 안정성까지 완전히 보장하지는 않는다.
현재 수직 접촉력 `foot_force_z`는 진단에만 남긴다. 검증되지 않은 힘 임계값을 단계 전환에 추가하지 않는다.
유지 시간도 정책 주기의 연속 표본에 대한 조건이다. 몸통·다리의 충돌 여유와 실제 충돌 원인은 아직 검증하지 않았다.
관절 명령 일괄 동결이나 착지 전 전진 보상 제거는 발을 단 앞으로 보내는 동작까지 방해할 수 있어 적용하지 않았다.

Student는 보상을 직접 최적화하지 않고 teacher 행동을 증류한다. 이 수정으로 기존 체크포인트의 동작이
자동 교정되지는 않는다. 관측 크기는 그대로지만 단계 판정이 바뀌므로 기존 teacher/student를 같은 수정 코드에서
다시 평가해야 한다. 새 보상 의도를 학습시키려면 teacher 재학습 후 student 재증류가 필요하다.
위의 기존 성공률은 수정 전 결과다. 해시가 고정된 `remote_eval_2850` 평가 사본에는 이 수정을 적용하지 않았다.

진단 실행 예시 (Isaac Lab이 설치된 환경에서):

```sh
uv run python scripts/eval_stairs.py --task Hexapod-Stair-Student-A --checkpoint <student.pt> --num_envs 16 --diagnostics outputs/student_trace.jsonl --diagnostic-envs 4
```

JSONL은 앞의 4개 환경의 첫 에피소드만 기록하며, 지정 경로는 새 파일이어야 한다.
`move`, `feet_up`, `body_counts`, `move_done`, `all_kept`, `move_ready_time`, `body_vx`, `foot_force_z`, 접촉력과 링크 이름이 들어간다.
`move`는 단계 증가 전 값이고, `just_done`은 그 step에서의 전환 여부다. 종료 step도 자동 리셋 전 상태를 보존한다.
`first_sampled_undesired_contact_links`는 처음 관측된 몸통·coxa·femur 접촉 후보이고,
`first_sampled_tibia_horizontal_contact_links`는 처음 관측된 tibia 수평 접촉 후보다.
동시에 잡힌 링크는 모두 기록한다. 접촉 이력 중 링크별 최대 힘 표본과 별도의 최대 수평 힘을 기록하므로,
큰 수직 지지력이 더 작은 수평 접촉을 가리지 않는다. 접촉 상대가 계단인지,
어느 물리 substep에서 먼저 충돌했는지까지 단정할 수 없다.

- MOVE에서 `feet_up=False`인데 `body_vx>0`이면 옮기는 발이 단 높이 아래인 상태에서 전진한 것이다. 이것만으로 student 문제라고 확정하지 말고 teacher의 같은 로그와 비교한다.
- 정상 전환 뒤 ADVANCE에서 접촉 후보가 나타나면 지지 상태와 몸통·다리 자세를 함께 확인한다.
